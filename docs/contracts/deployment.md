Owner: Isaac · Partners: every owner (per-service settings), Caleb (NetworkPolicy, Secrets, mTLS) · Code: `deploy/` · Status: **draft**, needs review by Caleb

> - **Hardening:** per-path and per-store NetworkPolicies; k3s secrets encryption.

**HA flag:** the chart's `ha` value runs a bank with replicas: Kafka 3 brokers (replication 3, `min.insync.replicas` 2, the offsets and transaction-state topics likewise), PostgreSQL 3 instances (a primary and two streaming replicas with automatic failover) and privacy node 2. `install.sh` sets it for the banks in `HA`: bank A on k3d (`k3d-up.sh`), which is one node, so failover there is pod-level only; every bank on EKS (`eks-up.sh`). Set it on a fresh bank: turning it on for a running one leaves the existing topics at replication 1, below `min.insync.replicas` 2, so every write fails.

**Pod security:** `install.sh` labels each bank namespace with the restricted Pod Security Standard: `enforce`, so Kubernetes rejects a non-compliant pod, and `warn`, so `helm` says why (otherwise the rejection shows only in the ReplicaSet's events). The chart's pods take their settings from `_helpers.tpl`, CloudNativePG's comply as shipped, and Strimzi runs with `STRIMZI_POD_SECURITY_PROVIDER_CLASS=restricted`. `replay` isn't labelled: on k3d its Job mounts a `hostPath` volume, which the profile forbids.

**EKS:** the account is an AWS Academy Learner Lab, which can't create IAM roles, so everything runs as the pre-made `LabRole` and Pod Identity is dropped. Pods take the role from the node's metadata service instead. The bank namespaces' default-deny policy blocks it (probed in `check-netpol.sh`), though a new pod may get through in the seconds before its policy applies. `deploy/eks-up.sh` sets it all up with the same chart as k3d (Environments, below), passing each bank's AWS endpoints from Terraform's `bank_values` output (`--set-json aws=...`). A bank found there runs no ingestor, summary or Valkey pods: the ingestor and summary service are Lambda function URLs (zips built by `deploy/lambda-zips.sh`) and Valkey is ElastiCache (Platform components, below).

Scope: one-command k3d setup, the per-bank Helm chart, image builds, EKS, monitoring and the evaluation harness.

## Namespaces and network paths

One namespace per bank: `bank-a`, `bank-b`, `bank-c`, each a release of the `deploy/charts/bank` Helm chart.

Current baseline (`bank-baseline` policy): deny all, then allow traffic within the bank's own namespace, DNS, the Kubernetes API (TCP 443/6443 to the chart's `apiServerCIDRs` only; `k3d-up.sh` pins the k3d node subnet to match; `eks-up.sh` passes the control plane's addresses and the `kubernetes` Service address, since pods share the VPC; `check-netpol.sh` probes that another 443 service stays blocked), and ingress from the `strimzi`, `cnpg-system` and `keda` operators. k3s applies a new pod's egress policy a few seconds after the pod starts, so its first connections can bypass it. Strimzi's own generated policies are turned off so that they can't open Kafka to other namespaces. Cross-bank traffic is blocked.

**pending work** (with Caleb): keep the default-deny baseline, add one small policy per store (Kafka, PostgreSQL, Valkey) allowing only labelled clients, and one allow rule per real path, each with an open/blocked probe pair in `check-netpol.sh`:

| Path | Rule |
| --- | --- |
| Privacy node ↔ other banks' privacy nodes | Ingress from the other two bank namespaces **and** `app: privacy-node` pods, gRPC port only, with matching egress. **Done** (`privacy-node-peers`), probed in `check-netpol.sh` |
| Replay → ingestor (k3d) | Ingress from the `replay` namespace to `app: ingestor` on its HTTP port. **Done** (`replay-to-ingestor`), probed in `check-netpol.sh` |
| Ingestor Lambda → Kafka (EKS) | Ingress from the VPC's CIDR to the brokers' `vpc` listener (9094). **Done** (`lambda-to-kafka`). A NetworkPolicy can't name the Lambda's security group, and pods share the VPC, so this opens each bank's Kafka listener to every pod: Kafka is no longer namespace-private on EKS, a stated cost. The security groups do restrict the Lambdas: each bank's reaches only its own bank's node ports |
| Scorer, privacy node → ElastiCache (EKS) | Egress to the VPC's CIDR on 6379. **Done** (`valkey-clients`), probed in `check-netpol.sh`. The VPC's CIDR covers every bank's ElastiCache, so this doesn't keep banks apart (Platform components, Valkey) |
| Case service → summary Lambda (EKS) | Egress to 443 outside the VPC, and to the node's metadata service (`169.254.169.254:80`) from `app: case` only, so it can sign the call as `LabRole`. **Done** (`case-to-summary`), probed in `check-netpol.sh`. This hands that pod the whole role: an accepted limitation of the lab account. Locally the summary container sits in the namespace |
| Privacy node → case service → summary service | Inside the bank, so the baseline allows it; `check-netpol.sh` probes the node → case path |
| Analyst → web UI | `kubectl port-forward -n bank-a svc/case 8000` only, no Ingress; access control is cluster RBAC |

The API-server rule should be narrowed from the whole k3d node subnet. On EKS the VPC CNI enforces the same policies and `check-netpol.sh` runs the same probes.
